> **Implementation note:** Repository hiện đã có các luồng quản trị người dùng, duyệt/từ chối POI, yêu cầu chỉnh sửa POI và xác thực. PRD này đề xuất bổ sung nhật ký kiểm toán tập trung; không khẳng định tính năng audit log đã được triển khai.

## 1. Overview

Audit Log cho phép Admin xem lại các hoạt động quan trọng đã xảy ra trong hệ thống, xác định ai thực hiện hành động nào, vào thời điểm nào, đối tượng nào bị tác động và kết quả ra sao. Tính năng hỗ trợ truy vết thay đổi, kiểm tra thao tác quản trị và điều tra sự cố.

Nhật ký được ghi ở backend, không phụ thuộc vào việc giao diện người dùng tải thành công. Người dùng thông thường và POI Owner không được phép xem nhật ký quản trị.

## 2. Problem Statement

Hiện hệ thống có các hành động có tác động đáng kể như quản lý tài khoản, thay đổi trạng thái người dùng, duyệt hoặc từ chối POI, yêu cầu chỉnh sửa địa điểm và đăng nhập. Nếu không có nhật ký tập trung, Admin khó xác định nguyên nhân của thay đổi, thời điểm diễn ra và tài khoản đã thực hiện thao tác.

## 3. Goals and Non-goals

### 3.1 Goals

- Ghi lại các hành động bảo mật và quản trị quan trọng ở phía backend.
- Lưu thông tin actor, action, resource, timestamp, outcome và correlation/request ID khi có.
- Cung cấp màn hình/API chỉ dành cho Admin để tìm kiếm, lọc, xem chi tiết nhật ký.
- Giữ nhật ký có tính nhất quán, giảm nguy cơ sửa/xóa trái phép.
- Không lưu mật khẩu, access token, OTP, secret hoặc dữ liệu nhạy cảm không cần thiết.

### 3.2 Non-goals

- Không thay thế hệ thống giám sát hạ tầng, application logs hoặc analytics.
- Không ghi toàn bộ request/response body.
- Không cho phép sửa hoặc xóa từng bản ghi audit thông qua giao diện.
- Không triển khai SIEM hay cảnh báo thời gian thực trong phạm vi đầu tiên.

## 4. Users and Permissions

| Actor | Permissions |
|---|---|
| Admin | Xem danh sách, lọc, phân trang và xem chi tiết audit events |
| POI Owner | Không được truy cập audit log quản trị |
| Public/anonymous visitor | Không được truy cập audit log |
| Backend service | Tạo bản ghi theo các sự kiện được quy định; không cung cấp API sửa/xóa cho client |

Mọi endpoint đọc audit log phải sử dụng cơ chế xác thực hiện có và dependency `get_current_admin`. Không được tin tưởng role do client tự gửi; danh tính/role phải được xác minh từ access token và tài khoản trong database.

## 5. User Stories

- **US13.1 — View audit events:** As an Admin, I want to view a chronological audit log so that I can review important system activity.
- **US13.2 — Filter events:** As an Admin, I want to filter by time range, actor, action, resource type, and outcome so that I can find relevant events efficiently.
- **US13.3 — Inspect an event:** As an Admin, I want to inspect the metadata and before/after summary of an event so that I can understand what changed.
- **US13.4 — Trace failed attempts:** As an Admin, I want to see selected failed authentication and authorization attempts so that I can investigate suspicious activity.
- **US13.5 — Protect log integrity:** As a system owner, I want audit records to be append-only to reduce the risk of tampering.

## 6. Functional Requirements

### FR-13.1 — Automatically record events

The backend shall write an audit record for the following event categories:

| Category | Events to record |
|---|---|
| Authentication | Successful login; failed login with a generic reason code; invalid/expired token or forbidden admin access when reliably detectable |
| User management | Create, update, activate/deactivate, or delete user; change role where supported |
| POI moderation (UC11) | Approve/reject submission; request revision; edit an existing POI |
| POI Owner registration (UC12) | Approve, reject, or delete a registration |
| Audit access | Admin views audit log or event details, if policy requires access auditing |

Only events that actually occurred should be marked successful. Rejected validation, missing resources, permission failures and database errors must not be represented as successful business actions. Failed operations may be recorded as outcome `failure` when useful and safe.

### FR-13.2 — Store audit records

Each record shall include:

| Field | Type / example | Requirement |
|---|---|---|
| `_id` | MongoDB ObjectId | Generated by MongoDB |
| `eventId` | UUID string | Unique event identifier |
| `occurredAt` | UTC ISO timestamp / BSON Date | Required; assigned by backend |
| `actorId` | User ObjectId string or null | Null for anonymous/system event |
| `actorRole` | `admin`, `poi_owner`, `anonymous`, `system` | Role at event time, where known |
| `actorEmail` | Normalized email or null | Optional snapshot; minimize personal data |
| `action` | `poi.approve`, `user.update` | Required, stable machine-readable name |
| `resourceType` | `poi_submission`, `poi`, `user`, `auth_session` | Required |
| `resourceId` | Internal ID or null | Required when a resource exists |
| `outcome` | `success`, `failure`, `denied` | Required |
| `summary` | Short human-readable description | Required; no secrets |
| `changes` | Selected field-level before/after values | Optional; allowlist only |
| `reasonCode` | `invalid_credentials`, `forbidden`, etc. | Optional; do not expose secrets |
| `requestId` | Request/correlation ID | Optional when middleware provides it |
| `ipAddress` | Truncated/masked IP | Optional; collect only when approved by privacy policy |
| `userAgent` | Short sanitized string | Optional; apply length limits |

Use UTC for timestamps and a documented, consistent action vocabulary. Do not store password hashes, raw passwords, access/refresh tokens, Authorization headers, OTPs, email verification codes, environment variables, database connection strings or complete request bodies. Before/after snapshots must use an explicit allowlist of non-sensitive fields.

### FR-13.3 — Audit viewer

The Admin interface shall provide:
- A newest-first table showing time, actor, role, action, resource, outcome and summary.
- Filters for start/end time, actor, action, resource type, outcome and keyword/resource ID.
- Pagination handled by the backend; default page size 25 and maximum page size 100.
- An event detail view showing all permitted metadata and selected field changes.
- Clear loading, empty, validation-error and server-error states.
- Date/time presentation in the user's local timezone while preserving UTC timestamps in storage/API.

### FR-13.4 — Search and pagination API

Proposed endpoints (subject to API review):

- `GET /api/v1/admin/audit-logs` — list/filter/paginate events.
- `GET /api/v1/admin/audit-logs/{event_id}` — retrieve one event.

Suggested query parameters:
- `from`, `to`: ISO-8601 timestamps.
- `actorId`, `action`, `resourceType`, `resourceId`, `outcome`.
- `q`: bounded search term for safe indexed fields.
- `page` and `pageSize` (maximum 100).

The API shall validate date ranges and query lengths. A response shall include items and pagination metadata, for example `items`, `page`, `pageSize`, `total`, and `hasNext`. The API shall not return internal MongoDB fields unless explicitly part of the response schema.

### FR-13.5 — Immutability and retention

- Client-facing APIs must not support edit or delete operations on audit records.
- Audit writes shall be centralized in a backend service/helper so event naming and redaction are consistent.
- Access to the MongoDB collection should follow least-privilege principles. Where deployment permits, separate write and read permissions or export logs to a more restricted sink.
- Retention duration must be configurable and approved by the project owner; the initial default proposal is 180 days, subject to privacy, storage and course-project requirements.
- Any scheduled cleanup/archival process must be explicit, monitored and documented. Do not add a TTL index until retention is approved.

## 7. Main Flow

1. An authenticated actor performs an action such as approving a POI submission.
2. The backend authenticates and authorizes the actor.
3. The backend validates the request and executes the business operation.
4. The backend creates an audit event with actor, action, resource, outcome, timestamp and safe metadata.
5. The Admin later opens **Audit Log** from the admin area.
6. The frontend calls the list endpoint; the backend verifies Admin privileges and returns filtered, paginated records.
7. The Admin applies filters or opens one record to inspect details.

### Alternative and exception flows

- **A1 — Validation/business rule failure:** Return the normal error response; if the event is security-relevant, write a failure/denied event with a safe reason code.
- **A2 — Database operation fails:** Do not write a success event. Report the application error and record a failure event if the audit storage is available.
- **A3 — Audit storage write fails after a high-risk operation:** The project must explicitly choose fail-open vs fail-closed per action. Default proposal: fail closed for security-critical operations only when transactional/atomic behavior is feasible; otherwise keep the response truthful, emit an operational error and do not claim that an audit record exists.
- **A4 — Non-Admin opens audit endpoint:** Return HTTP 403; do not disclose audit records.
- **A5 — No matching records:** Return HTTP 200 with an empty item list and valid pagination metadata.
- **A6 — Invalid date range or pagination:** Return HTTP 422 with a safe validation message.

## 8. Data and Technical Design

### 8.1 MongoDB collection

Create a dedicated collection named `audit_logs`. Recommended indexes:
- `occurredAt: -1` for chronological retrieval.
- `eventId: 1` unique.
- `actorId: 1, occurredAt: -1`.
- `action: 1, occurredAt: -1`.
- `resourceType: 1, resourceId: 1, occurredAt: -1`.
- `outcome: 1, occurredAt: -1`.

Create indexes at application initialization or via a documented migration/script, not on every list request. Validate index choices against actual query patterns.

### 8.2 Backend integration

Proposed implementation components:
- `backend/app/audit/service.py`: event creation, field allowlisting, redaction and canonical event names.
- `backend/app/admin/audit_router.py`: Admin-only list/detail endpoints.
- Register the router in `backend/app/main.py`.
- Optional frontend component/service under `web-app/src/components/admin` and `web-app/src/services` after API contract approval.

Business routers should call the shared audit service after determining the outcome. Avoid duplicating raw insert logic across individual endpoints. For actions spanning multiple MongoDB writes, define which state transition the audit event represents and prefer a MongoDB transaction when supported/configured; otherwise document partial-failure behavior.

## 9. Non-functional Requirements

- **Security:** Every read endpoint must enforce Admin authorization server-side. Never rely on frontend route hiding.
- **Privacy:** Apply data minimization and redaction. Do not store secrets or unnecessary personal data.
- **Integrity:** Records are append-only through the application interface; privileged database administrators remain a separate trust boundary.
- **Performance:** Paginated list queries should use indexes and avoid unbounded collection scans. Target p95 under 500 ms for common queries at the expected course-project scale, subject to test environment.
- **Reliability:** Audit failures must be observable through server-side operational logging without recursive attempts to audit audit failures.
- **Consistency:** Use UTC timestamps, stable action identifiers, bounded field lengths and a common response schema.
- **Accessibility/usability:** Table and filter controls must be keyboard accessible and display understandable empty/error states.

## 10. Acceptance Criteria

1. An authenticated Admin can retrieve audit events newest-first with pagination.
2. A non-Admin or anonymous user cannot read the audit list or event details.
3. Approving or rejecting a POI submission creates exactly one corresponding success event for the completed transition.
4. Updating or changing a user's status creates an event that identifies the actor, action and affected user without exposing credentials.
5. Failed authentication events, when logged, use safe reason codes and never reveal whether sensitive account details beyond the intended public error contract.
6. Filters by date range, action, actor, resource and outcome return only matching records.
7. Invalid time ranges and out-of-range pagination values are rejected with validation errors.
8. A missing event returns 404; an empty search result returns 200 with an empty list.
9. No API or UI path allows a regular user to modify or delete audit entries.
10. Unit/integration tests cover authorization, event creation, redaction, filter validation, pagination and database failure behavior.
11. Automated tests verify that passwords, tokens, OTPs and secrets never appear in stored audit events.
12. The feature documentation clearly states the retention policy and the chosen behavior when audit persistence fails.

- Confirm retention period and whether IP address/user-agent collection is allowed.
- Confirm whether authentication failures should be written synchronously or through a separate security logging path.
- Decide fail-open/fail-closed behavior for high-risk actions if audit persistence fails.
- Confirm the intended PRD/UC naming convention with the project’s existing requirements set.
- Review indexes and performance targets against the actual expected dataset.

## 13. Out of Scope / Future Enhancements

- Export to CSV/JSON with permission checks and export-event auditing.
- Alerts for repeated failed logins or unusual administrative activity.
- Tamper-evident hash chaining or remote immutable log storage.
- Advanced full-text search and dashboards.
